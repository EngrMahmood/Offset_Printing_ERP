# Maintenance — user guide

## For machine operators

**Report a problem** (Maintenance → Report a problem)
1. Pick the machine.
2. Describe the problem in your own words.
3. Answer **Has the machine stopped?**
   - **Yes** — the ticket is marked *Critical*, the machine's downtime starts, and maintenance is alerted.
   - **No** — the ticket is *Medium*; maintenance decides the final priority.
4. Add a photo if you can, then submit.

You get a ticket number (MNT-2026-0001). If the machine already has an open ticket you will see it first; only report again if it is a different fault. Pressing submit twice will not create two tickets.

**Follow it up:** *My tickets* shows only what you reported, with the current status in plain words (for example "Waiting for spare parts" or "Repair finished — needs a test run"). You can add a comment or a photo. You cannot change priority, costs or the machine's state.

## For maintenance engineers

| Step | Button | What it needs |
|---|---|---|
| New complaint | **Triage This Complaint** | Classify type, priority, fault types, who does it. Classifying as *Breakdown* marks the machine as stopped. |
| Start work | **Start / Resume Repair** | — |
| Parts or vendor needed | **Waiting for Parts / Vendor** | Add the spare part or service line, then *Raise demand* (creates the Supply Chain request). |
| Work finished | **Repair Completed** | **Diagnosis / root cause** and **repair action** filled in; labour hours (actual work, not waiting). |
| Test the machine | set **Machine test result** | *Passed* before verifying. If the test fails, use **Start / Resume Repair** with a reason. |
| Confirm | **Test Passed — Verify** | Records who verified and when. **This is when the machine's downtime ends.** |
| Finish | **Close Ticket** | — |
| Not a real fault | **Cancel Ticket** | A reason. If the ticket had stopped the machine you must say whether the machine is running again, or is still down because another active ticket covers it. |

Rules worth knowing
- *Repair Completed* does **not** end downtime — only a verified, tested repair (or a confirmed "machine is running" at cancellation) does.
- If two tickets stop the same machine, downtime continues until the **last** one is verified.
- A closed ticket can be reopened only by a manager/admin, with a reason.
- Invalid moves show a message and change nothing.

## For managers
Reports, downtime history and the Excel export are limited to maintenance staff. Everything is recorded in each ticket's activity log (who, when, from/to status, reason).

## Safety
The steps above are the system workflow, not repair instructions. Electrical, pneumatic and guarding work must follow your factory's approved safety procedures and be done only by qualified people.

## Preventive maintenance (engineers)

- Maintenance → PM plans lists every plan with a plain state: *Overdue*, *Due in N days*, *Upcoming*. Edit or disable a plan from the list.
- A plan runs **every N days** or **every N impressions**. Impression plans count impressions from Production entries, so they are only as complete as those entries; a new impression plan starts counting from the machine's current total.
- When a plan falls due the system raises **one** ticket automatically (checked every 30 minutes), with the plan's instructions and its own checklist. A plan can never raise two tickets for the same due occurrence.
- Open the ticket, tick each checklist item and write any finding. The job cannot be completed until every item is ticked. Verifying the ticket records the plan's *last done* date.
- Overdue tickets remind the engineers (and the assigned technician) once a week.
- The checklist must be approved for the machine type by your maintenance/HSE team.

## Reports (staff)
Pick a date range. The page shows breakdowns, downtime hours, MTTR, repair versus waiting time, repeat faults and PM compliance, and explains how each number is calculated.

## For administrators
PM tickets are generated by an in-process scheduler, like the bots and backups. On a standby server that mirrors the primary database set `MAINTENANCE_INPROCESS_SCHEDULER=False` in its `.env`. To run it by hand at any time: `python manage.py generate_due_pm_records` (safe to repeat).

## The three windows

1. **Report a problem** — where operators raise a ticket (unchanged).
2. **Machines** — every machine with maintenance activity, stopped machines first. Each machine opens to show all of its tickets (operators see only their own), plus how long it has been stopped and which step it is in right now.
3. **Downtime** (engineers/managers) — where the stopped time went, **by process step and by owner**:
   - *Internal maintenance team*: waiting for maintenance to respond, waiting to start, repair, testing, and parts received but not yet fitted.
   - *Supply Chain / Procurement*: request review and approval, purchasing (PR to PO).
   - *Supplier delivery*: PO to receipt.
   - *Outside repair vendor*.

   "Waiting right now" lists machines held up at this moment, with the Item Request, supplier, the stage it has reached and how long it has waited. "Longest waits" gives the list to take to Procurement or a vendor.

### What the workflow now requires
- Moving a ticket to **Waiting for Parts** needs at least one spare-part line; any line not yet requested is raised in Supply Chain automatically, so the wait is always traceable. **Waiting for Vendor** works the same way with a service job.
- When Supply Chain records receipt of all the parts a ticket is waiting for, the engineers and the assignee are notified once, so a delivery never sits unnoticed while the machine is down.
- Parts-wait time is split using the dates on the Item Request (request, PR, PO, receipt), so keep those dates up to date in Supply Chain.
